# E 端会话教训摘要

本文件是 2026-10-28 r258 移交前，两台开发机并行期间的协作教训摘要。E 端已在 r258 检查点停止新增功能并退场（称谓定义见 [术语表](GLOSSARY.md)），此后开发由 N 端单机承担。**保留本文件的目的只有一个：不让同样的缺陷再犯一次。**

原始会话记录（147 条人工指令、189 次上下文压缩）体量约 1.4 MB，只在本机保留，不提交。本文件是脱敏摘要，不含书名、设备地址、私人路径和截图。

## 一、移交前的工作模式及其失效

并行期间采用「N 端实现 → 生成自然语言交接文本 → E 端手工整合后重新提交」的模式。E 端**不合并分支、不 cherry-pick**，因此两侧提交历史互不相干。

这个模式已随 E 端退场而终止，`docs/DUAL-MACHINE-HANDOFF.md` 顶部已标注失效。回顾它的代价，是为了避免将来重新引入同类流程：

| 现象 | 根因 |
| --- | --- |
| N 端分支「本地领先但远端查不到」 | 两侧历史无关，N 端以为推送即可见 |
| E 端查到的 origin 是另一个同名仓库，找不到 N 端分支 | 两个同名仓库并存，远端配置不同 |
| 交接文本传输出现乱码 | 靠自然语言传技术细节，无机器校验 |
| N 端对 ZIP 行为的推断被 E 端当面纠正 | 推断未经本地验证就当结论发出 |

**结论**：跨机器交接如果必须存在，交付物应是**可机器校验的差异**（补丁、提交号、哈希），而不是自然语言描述。

## 四、反复出现的 ArkUI 节点复用缺陷

`ForEach` 的 key 只用 `id`，导致状态变更后 ArkUI 复用旧节点、界面不刷新。这个模式在本项目犯了四次，最终统一改为键函数。详见 [编码规约](CODE-CONVENTIONS.md) 第一节。

同一模式犯四次说明问题不在能力而在规约：**缺一条「列表必须回答显示什么」的检查，就会每个列表各犯一次。**

## 五、仍然有效的经验

1. **证据分级不可省**。并行期间反复被强调的是「一方的设备结果不能写成另一方已验证」。E 端退场后这条依然成立，只是对象变成「构建通过」与「设备验收」的区分，已固化为 [验证记录](VALIDATION.md) 开头的三级口径。
2. **只做当前模块**。E 端 147 条指令里，凡出现范围蔓延都被用户当场纠回。这条已在 `AGENTS.md` 和 [项目队列](PROJECT.md) 中保留。
3. **交付前跑目标工程构建**。这是唯一被历史证明「省掉就必然出问题」的步骤。
