# 盘点规约

本文件收纳**盘点方法**类的规则：怎么划上游接触面、怎么定行粒度、怎么判定「已接/未接/不适用」、怎么算盘完。

它和 [编码规约](CODE-CONVENTIONS.md) 分工明确：

- **本文件管「盘什么、盘到什么程度」**——读者是派活的人和做盘点的人。
- [编码规约](CODE-CONVENTIONS.md) 管「写代码时别踩什么坑」——读者是改代码的人。

从 `docs/CODE-CONVENTIONS.md` 拆出来的原因：那份文件里实现类 5 节与盘点类 2 节混在一起，长到 4000 多字符的第四节把其余各节压得没人看。拆开后两边都能单独引用。

---

## 一、上游事实必须先检索再断言

「上游没有实现」「上游不支持某功能」是本项目代价最高的断言，因为它直接决定方案走向。历史上有三处断言错误：

| 错误断言 | 实际 |
| --- | --- |
| 上游没有高亮规则备份 | `app/src/main/java/io/legado/app/help/storage/Backup.kt:212` 已有 `highlightRule.json` 写入，`Restore.kt:269-270` 已有 `replaceAll` |
| 字段名不一致需映射层 | 本地 33 字段与上游 `data/entities/HighlightRule.kt` 36 字段中同名同义 33/33，无需映射 |
| `viewBox="92 92 186 186"` 需修正 | 首行注释写明由 `ic_launcher_foreground.xml` 原样转换，是刻意裁剪 |

**规则**：写「上游没有 X」时必须附检索命令与命中位置；无检索证据的此类结论不得进入任务清单。同理，判断某个转换方法「零调用所以功能没接入」时，要连同调用方一起查（历史上有一次正是因为只查方法定义而误判）。

**为什么**：这条断言的错误方向是单向的——说「上游没有」会让整件事被判定为「不需要做」，于是缺口被永久性抹掉；说「上游有」最多是白做一轮，还能查出来。历史上三次误判全部朝「上游没有」的方向错，所以对这类断言要求最严。

## 二、模块对照必须一次盘完

按单个上游文件逐轮读改，每轮只发现一两个缺口，反复构建和上设备，是历史上最长的返工循环。书签模块出现 15 个提交、每轮 1~6 项，根因是枚举单位取成了「一个文件」。

**为什么**：返工成本不对称。一次盘完多花的是读代码的时间，逐文件读改多花的是构建 + 上设备的时间，而后者每轮都要重来。书签模块 15 个提交就是这条规则的来历（2026-10，`docs/history/validation/` 有当轮记录）。

**枚举上游接触面**：按内容引用划，不按文件名划。用 `grep -rl "<类别关键词>" app/src/main/java --include=*.kt`，不是 `find -name`。书签模块文件名 `find -iname '*bookmark*'` 命中 20 个、内容引用 `grep -rlE 'Bookmark|BookMarking'` 命中 63 个，差三倍（2026-10-30 在 `<上游根>/app/src/main/java` 实测，关键词见 [对照关键词](parity/KEYWORDS.md)）。

**先出对照表，再写第一行代码**。表中每行是一次用户可感知的操作，状态只允许 `已接`/`未接`/`不适用` 四值；`不适用` 须写理由（下限见本节末的检查清单），盘点结束时不得残留未判项。表的位置与字段见 [ZIP 兼容总账](parity/STATUS.md)。

**盘点单位是界面，不是按钮**。盘某个功能时，先定位它所在的界面，然后把这个界面的**完整构成**列进表——包括与当前功能无关的部分。判定「涉及这个界面」只要满足一条：进了这个页、开了这个弹层、这个界面被改动。未迁移的部分显式标 `未接` 并写明差距，归到对应界面的说明里，不要因为「与本次功能无关」就省略。

**每行的 `ZIP 类别` 按「会动到哪个类别」判，不按「数据落在哪」判**。跨类项（一行同时动两三个类别的键或文件）必须标全，否则按类别派活时会被漏掉一半。`—`（参与备份但不受任何忽略开关控制）与 `不备份`（连 `config.xml` 都进不去）是两档不同的取值，都不属于 28 类，按类别名派活覆盖不到，必须单独派。四档取值的完整语义与判定依据见[备份恢复](BACKUP-RESTORE.md)的「三张对照表的「ZIP 类别」列怎么读」。

反例（2026-10-30 实测）：盘「划线/笔记」时，长按选词菜单只记了 2 行（把 8 个内置项压成一行、第三方扩展一行）。而该界面的实际构成是：上游 `ReadBookController.kt:2133-2155` 的 **14 个内置项**（复制/分享/浏览器/朗读/书签/标记/词典/替换/编辑/AI 清洗/AI 改写/搜索内容/插入 BGM 前/后），每项都有图标（`TextActionSelectionMenu.kt:585-600`），两套形态由 `expandTextMenu` 切换（`QuickMenuView` 一排 + 「更多」浮层 / `MultiLineMenuView` 多行平铺），项级 `showState` 三档（一级/折叠/隐藏），外加一个 460 行的菜单管理器页 `TextSelectMenuConfigSheet.kt` 与 `textSelectMenuConfig` 一条持久化链路。按按钮盘只有 2 行，按界面盘是 14 项 + 1 页 + 1 条链路。

_避免_：只盘「与本功能相关的按钮」，把同一界面上其余未迁移部分从表里抹掉——这类漏法在书签、划线、书架三张表上都出现过。

**完成判据是覆盖证明，不是「无待定」**。上游接触面的每一个 `.kt` 文件都必须被显式分配到「已映射到某行」或「已排除 + 理由」二者之一，表格行数由这个分配决定。只满足「表中无空行、无待定」不算盘完——行数由盘点者决定，写多少行就有多少行，该判据证明的是表格自洽，不是上游被覆盖。用 `./scripts/upstream-surface.sh --coverage <类别> <表格路径>` 生成待分配的清单。

**覆盖证明通过 ≠ 上游被覆盖，关键词本身可能选错。** 这个判据的分子分母都由关键词决定，关键词只认「实体类名」时会系统性漏掉一整层。上游的类别有两副面孔——实体类名（`data/entities/Bookmark.kt`）与忽略项键名字符串（`help/storage/BackupConfig.kt` 的 `dbKeyBookmark = "bookmark"`），而导出/恢复主文件 `help/storage/Backup.kt` 里一个实体类名都不出现（`grep -cE "Bookmark|BookMarking"` = 0），19 个类别全写成 `dbIsNotIgnored("bookmark")`。按实体类名选词，`Backup.kt` 就不在接触面里——而它正是该类别导出逻辑的唯一所在地，于是「表格显示通过、导出逻辑从未被检查」长期共存。r294 给 28 类全部补上键名字面量后 `Backup.kt` 才进入接触面；补完后仍有 18 个存储层文件对全部 28 类零命中，它们的共同点是「处理所有类别一起的动作」，只能靠[书籍总账](parity/BOOKSHELF.md)的 E 备份恢复块整块承载。新增或复核类别关键词时，先把「这个类别的逻辑会不会出现在按类别名检索不到的位置」问一遍。

**为什么**：这是覆盖证明唯一的失效模式，而且它失效时表格是「全过」的——不报错、不留痕。2026-10 之前 `readConfig` 用控制类型的开关名当关键词，只命中 2 个文件，等于「2 个文件全过」，自证成功了好几轮才发现。

**「已接」的证据必须是「看到什么」，不是「键落库了」。** 字段对上不等于行为对上。`pageAnim` 这条判过 `已接`：存储键同名对位、默认值一致、面板能改、能落库——但上游 `COVER` 是「新页在原位不动、旧页盖上去滑走」（`feature/reader/core/transition/ReaderPageTransition.kt` 的 `transforms(COVER)` 里 `next = ReaderPageTransform()` 位移为 0、`currentOnTop = true`），本地 `ReaderPage.ets:1683-1701` 是「旧页滑出 → 中点切页 → 新页从另一侧滑入」，中间 360ms 屏幕是空的。数据层完全等价，屏幕效果完全不是一回事，表上写的是 `已接`。

因此凡是改变屏幕呈现的行（排版、翻页、渲染、动画、手势判定、绘制），验收列必须写一句**屏幕现象**。写不出这句话就只能判 `未接`，哪怕字段全对、面板全上屏——字段级证据只能支撑「字段已接」，不能支撑「这项已接」。

**为什么**：验收列写「能改、能存、重启保持」时，验的是存储链路；而用户感知到的只有屏幕。两者在绝大多数情况下同向，所以不会有人主动怀疑——这正是它危险的地方。2026-11 那次翻页空白的排查里，表上是 `已接`，实际要重写渲染层。

**「架构差异」不能单独作为排除理由。** 上游 `feature/reader/ReaderCanvasSurface.kt` 是 3747 行的 Compose `Canvas` 自绘管线，本地是 ArkUI 组件树；拿这条理由把它整体排除，等于把渲染主体排除在检查范围之外（[书签对照表](parity/ZIP-BOOKMARK.md) 的「已排除：渲染管线差异」就是这么写的，两行都写了「架构差异不是缺口」）。

排除「实现方式」可以，但必须同时回答一句：**上游这个实现方式带来的效果，由哪一行负责？** 没有任何一行负责就不能排除，必须新开块。判断依据是「用户能不能感知到差别」，不是「代码结构像不像」。

**为什么**：架构差异是事实，但它不是「不做」的理由。上游用画布是为了逐行绘制、不重建节点树；本地用组件树，这个效果就没人负责了，而它恰好是翻页空白与开书跳变的根因。

**渲染与公共管线不属于任何类别，必须单独立块。** 有一层代码对所有类别关键词零命中，因为它们处理的是「所有类别一起」的动作：`help/storage/` 的整批规划与规整、`feature/reader/core/` 的分页器 / 文字整形 / 转场策略 / 选区几何。按类别名派活永远覆盖不到，散在「已排除」里就永久隐身。处置方式是整块承载——[书籍总账](parity/BOOKSHELF.md) 的 E 备份恢复块是这个模式，渲染管线同样要单独立块。

**语义等价比行为等价更深一层：同样的输入要给同样的输出。** 上游这批重构把判定逻辑大量抽成了纯函数（`BookRestorePlanner.planBookRestore`、`BackupConfig.keyIsNotIgnore`、`BookExtensions.isLocal`、`ReaderPageTransitionPolicy.release` 的 `commitProgress = 0.35f` / `flingVelocityPxPerSecond = 900f`、`AppUiConfiguration.isDarkTheme`、`RestoreConfigNormalizer.normalizeConfigMap`）。纯函数意味着可以逐条对拍：把上游判定分支全排列成决策表，一行一个用例，本地实现必须逐行通过。

这类差异的共同特征是**正常路径一致、边界路径才分叉**，人工点一遍永远发现不了。仓库里已经有一例：`ReaderPage.ets:1999 getMarkingForTextRange` 只判区间相交、不看 `selectedText`，而上游 `domain/model/BookContentProcessEngine.kt:101-131` 按「选中文本 → 去空白 → 全空白归一化」三级退让重定位——用户不改字号时两者一模一样，一改字号本地高亮就落到错误的文字上。这条已登记在[已知问题](KNOWN-ISSUES.md)，但它是散文，不是可复跑的断言。

**盘点结论必须当轮落盘，没落盘等于没盘**。每轮盘点结束必须把结论写进对照表或已知问题，不能只留在对话里。理由：对话会被压缩，未落盘的结论等于没产生，同一件事会被重新发现第三次。

**验收合并成一次**：全部差异改完，构建一次，上设备走完整清单。不以单个文件的差异作为一轮交付。

违反后会发生什么：差异清单不完整，每一轮都以「又发现一处」结束，构建与设备验证被重复消耗，交付节奏由未被发现的缺口数量决定。

## 三、`不适用` 的证据下限

判 `不适用` 不是「不想做」的出口。四张对照表里现有 11 个「已排除」小节、112 个条目，其中 39 条的理由是叙述式的、连行号都没有——那等于没写。所以这条判据要有下限。

判 `不适用` 之前，先归到下面四类之一，并给出对应的证据形态：

| 类型 | 适用情形 | 必须给出的证据 |
| --- | --- | --- |
| 上游无此行为 | 上游确实没有这个功能，或代码里有但从未接线 | 检索命令 + 零命中输出；或上游文件:行号 + 引用其注释原文（如「effect not currently emitted」） |
| 平台无此能力 | 该机制在 HarmonyOS 上不存在 | SDK 声明文件路径 + 行号 + 该能力在本平台缺失的说明 |
| 范围之外 | 属 [项目范围](PROJECT.md) 明列的不做项 | `PROJECT.md` 的行号 |
| 数据层无独立界面 | 纯数据层/DAO/实体，用户感知不到 | 它被哪个界面块消费（落点块名 + 行号） |

**一条都写不出，就不能判 `不适用`**——降级为 `未接`，写进 [已知问题](KNOWN-ISSUES.md) 并说明卡在哪。

**为什么**：`不适用` 是唯一一个「不需要再做」的判定，所以它天然会被当成出口。加下限不是不信任盘点者，是让后来的人能复核——一条没有证据的 `不适用`，读者无法判断它是真的不存在，还是当时没想到。

**已有条目的处置**：39 条叙述式理由不逐个补行号，改一张「落点映射表」（上游文件 → 被哪个界面块消费）。映射到具体块即视为已给证据；映射不到的，按上表四类之一重判。

## 四、验收等级与上游成对核实

设备验收三级口径定义在 [验证记录](VALIDATION.md) 开头的「验证等级口径」，本文件只补第四级：凡是「与上游对齐」的交付，除了本地走通，还要能说清**与上游的一致程度**。

**为什么**：前三级验的是「本地能不能用」，验不了「用起来是不是同一套逻辑」。而本项目的长期目标是完全兼容上游，所以「能用」与「一致」是两件事。

第四级有两种形态，任选其一即可（按证据可得性选，不是按严格程度选）：

| 形态 | 适用条件 | 做法 |
| --- | --- | --- |
| 成对截图 | 上游有该界面的既有截图 | 贴上游截图与本机截图并排，写出「一致项 / 差异项」 |
| 参数核对 | 上游无截图，但源码里有明确绘制参数 | 逐项写「上游参数 X（文件:行）→ 本地实现 Y（文件:行）→ 差异 Z」 |

**这台机器的现实约束**（2026-11 实测，写在这是为了让后来的人不必重新发现）：上游仓库**没有 APK、没有 adb、没有 Android SDK**，所以跑不起上游应用；上游截图存量很少（`project-resources/legado-with-MD3/screenshots/android` 43 张、`comparison` 3 张）。因此「参数核对」是主力形态，成对截图只在有存量截图时用。

上游自己写了这套方法：`<上游根>/docs/dev/track-c3-reader-parity-baseline.md`，含固定条件表（同一真机、同一构建、同一本书、同一页位置）与成对截图脚本。要动渲染类改动时先读它。

上游说明文档还有几份与本项目直接相关，开工前值得先读：`docs/dev/track-e-reader-settings-udf-plan.md`（阅读设置两套存储底座的语义对照，并明写「本轨道不改渲染方式」）、`docs/dev/kmp-cmp-modernization.md`、`docs/dev/mad-modernization-plan.md`、`docs/dev/track-c-compose-reader-plan.md`。**先读上游自己写的方案，能省掉一圈自己重新推演的时间**——这是本项目反复出现「推演完才发现上游文档里已经写了」之后的结论。

## 五、三段分工：取证、判断、实现

派活前先判断这件事属于哪一段，三段的准入条件不同。分段的依据不是「任务大小」，而是**做错了会不会被硬信号抓住**。

| 段 | 产出 | 准入条件 |
| --- | --- | --- |
| 取证 | 文件清单、行数、`grep` 结果、`--coverage` 输出 | **只许报材料，不许下结论** |
| 判断 | 归属、`已接/未接/不适用`、「上游到底怎么做的」、完成态定义 | 必须能回答「上游有没有这个」 |
| 实现 | 代码改动 + 可执行验证 | 完成态已写成可复跑的命令或可指认的屏幕位置 |

**验收不并进这三段，但也不必单列为第四段**——它是一条硬约束，不是一道工序：**实现方不得自己给自己验收**。谁来跑不指定，前提是它拿到的输入只有判断段写下的完成态和实现的交付物，**不拿实现的说明文字**。做法见本节末尾。

**为什么这么分**：取证的错误**有硬信号**（脚本跑一遍就能发现清单不对）；判断的错误**没有硬信号**，而且会推迟到实现阶段才暴露成「按表做完，结果还是不对」。历史上三次都是这个形状：

| 表上写的 | 实际 | 代价 |
| --- | --- | --- |
| `readConfig` 覆盖证明 76/76 全过 | 关键词是开关名，只命中 2 个文件，等于自证成功 | 阅读界面重盘到 107 才真实 |
| `localBook` 28/28 全过 | `help/storage/BookRestorePlanner.kt` 根本不在那 28 个文件里 | 三块恢复期语义长期空白 |
| 深色模式 r298「护眼不改变任何像素」 | `Index.ets:6759` 早有 `.sepia()` | r301/r306 两次自查推翻 |

**取证段的任务书必须写死一句**：「只许报告文件清单、行数、`grep` 结果；不许写『已接 / 未接』。」不写这句，取证方会顺手把结论也下了，而那些结论恰恰是最不该由它给的。

**判断段的产出就是给实现段的任务书**，所以要写成读者不必重新推演就能开工的样子：完成态三条、不在范围内、约束（含所有「不要做」）。**「不要做」比「要做」更省返工**——实现方看到一大套现成代码，不会自己问「上游有没有这个」。

**跨模型派活时，唯一可用的机制是 `workflow` 工具的 `agent(prompt, opts)` 带 `provider` / `model` 覆盖**，把某一段派给别的模型跑。这是「派活给别的模型」，不是「自己切换模型」——主会话不会因为本文件这样写就换模型，模型选择始终是会话属性，由人决定。本文件只管**怎么切段**，不管哪一段该配哪个模型；分段的目的是让每一段的输入输出边界清楚，至于由谁来做，按当时可用的资源定。

**三段的验收动作各自独立，不要合并**：
1. 取证段：复跑它给出的命令，数字对不上就退回重做。
2. 判断段：检查每行有没有可复跑的验证命令，没有就不算判断完。
3. 实现段：交付物必须是「截图 + 指认屏幕位置 + 可复跑命令」，不能是「改完了」。**实现方不宣布通过**，通过与否由另一次独立的验收跑决定（见下）。

**验收由谁跑，不指定**。验收这件事能不能成立，取决于输入是不是干净的，与跑的人是谁无关。**给还是不给实现的说明文字，是这件事成不成立的唯一变量。**

**为什么验收必须换人**：实现的错误大部分有硬信号（构建失败、截图不对、`assembleHap` 报错），但有一类没有——「屏幕上那个东西就是不对」。实测两次：画布会话阶段 A 报「完成」，而 `reader/ReaderCanvasSurface.ets` 里 `selection` 命中 0，长按选词整条链路是死的；阅读界面会话报「五处差异已全部对齐」，用户回「标题还是居中，翻页动画卡片依旧看不到」，根因是两处 `Row` / `Column` 缺 `.width('100%')`。两次都没自查出来。

这两次的共同点是**实现方自己给自己验收**：它知道自己改了哪几行，于是会去验证「我改的那几行生效了」，而不是验证「完成态成立」。画布那次它验的是折页弧度、带图重排、页眉页脚，这三条确实改了，`selection` 那条没人问。所以验收必须换人，而且换的人不拿实现方的说明。

**验收任务书怎么写**：只给两样东西——判断段写下的完成态（原样，不改写），和实现的交付物（截图、日志、构建产物）。**不给实现的说明文字**。理由：实现方的说明会把它没做到的部分描述成「已按计划完成」，验收方读到就先信了一半；只给完成态和证据，验收方才会去数「这条到底成不成立」。判 `不通过` 时只写「第几条没过 + 复跑命令的原始输出」，不要写「建议这样改」——那是下一轮判断段的事，验收方写建议等于顺手做了判断。
