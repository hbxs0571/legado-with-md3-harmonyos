# 编码规约

本文件收纳已经踩过的**实现类**缺陷，写成可对照的检查项。它不是风格指南，每条都对应一次真实故障。

**盘点方法不在这里**——怎么划上游接触面、怎么定行粒度、怎么判「已接/未接/不适用」、怎么算盘完，见 [盘点规约](PARITY-RULES.md)。两份文件按读者分工：本文件给改代码的人看，那份给派活和做盘点的人看。

## 一、ForEach 的 key 必须覆盖会变的展示字段

**规则**：`ForEach` 的键函数不得只返回 `item.id`。只要条目外观依赖某个可变更字段，该字段就必须进入 key，否则 ArkUI 会复用旧节点，出现「数据已改、界面还是旧的」。

原因是 ArkUI 按 key 做节点复用：key 不变即视为同一条目，只更新绑定的属性值；而条目内部由 `if`/`Text` 直接读取的字段不会重新求值。

**为什么**：这个模式在本项目犯了四次（书架卡片、替换规则、标注、高亮规则各一次），每次的表现都是「改完状态界面不动，退出重进才对」，排查时容易怀疑数据层。

**本项目已统一改用键函数的四处**（改这些文件时不要退回 `item.id`）：

| 键函数 | 位置 | 纳入 key 的字段 |
| --- | --- | --- |
| `replaceRuleRowKey(rule)` | `entry/src/main/ets/model/ReplaceRule.ets:19` | `id`、`isEnabled`、`name`、`group`、`pattern`、`replacement`、`scope`、`excludeScope`、两个 scope 布尔、`isRegex` |
| `bookCardKey(book)` | `entry/src/main/ets/pages/BookshelfPage.ets:64` | `id`、`chapterCount`、`chapterIndex`、`chapterProgress`、`coverMark`、`bodyMissing` |
| `markingItemKey(marking)` | `entry/src/main/ets/pages/CatalogPage.ets:136` | `id`、`effect`、`color`、`note`、`enabled` |
| `ruleItemKey(rule)` | `entry/src/main/ets/pages/ReaderHighlightRuleSheet.ets:193` | `id`、`enabled`、`position`、`name`、`pattern`、`underlineMode` |

共享模型上的键函数放在模型文件里（如 `ReplaceRule.ets`），页面私有的放页面内，两者不要互相复制。

**新增列表时**：先问「这条目显示什么」，把其中所有随状态变化的字段全部拼进 key。只有纯静态条目（打开后内容永不改变，如搜索历史）才可以用 `item.id`。

**检查方法**：改完列表页后，在一次运行内切换条目状态（启停、选中、改样式），确认条目文案/颜色即时变化，无需退出重进。

## 二、存储与备份改动必须同时交代三件事

历史缺陷里有四处都出在「只写了主路径」：

| 缺陷 | 漏掉的是什么 |
| --- | --- |
| 备份 `config.xml` 创建顺序错 | 写入顺序（配置尚未成形就被打包） |
| 恢复合并漏 `latestChapterTime`/`durChapterTime`/`order` | 读回字段与写入字段不对齐 |
| 键名写成变量名 `bookshelfLayoutPortrait`（字符串值不同） | 键名字面量未核对 |
| 保存失败仍更新界面缓存 | 失败态回滚 |

因此任何涉及持久化、序列化、ZIP 备份恢复的改动，交付说明里必须写清：

1. **写入顺序**：哪些键必须在哪些键之前落盘，`config.xml` 与各 JSON 的生成先后。
2. **读取路径**：旧版本数据怎么读（保留几个旧版分支）、字段索引是否有位移、缺失字段用什么默认值。
3. **失败态**：写盘失败时界面与内存缓存如何表现，是否回滚，用户看到什么。

**键名核对**：序列化键一律写字面量字符串，不写变量名。改完用 `grep` 回读一次实际写入的字符串，与 Android 侧键名逐字比对。

**为什么**：备份是唯一会跨设备、跨版本、跨进程流失数据的路径，出错时用户已经换机了，没有第二次机会。上面四条各自都造成过一次「备份看起来成功、恢复后少东西」。

## 三、构建不是可选项

每次源码改动后必须执行一次 `assembleHap`。命令见 [构建说明](BUILDING.md)。历史上有一次交付因 ArkTS 不接受对象展开写法而在目标工程构建失败，N 端未跑构建即交出。构建通过也不等于功能正确，等级口径见 [验证记录](VALIDATION.md) 开头的「验证等级口径」。

**为什么**：ArkTS 的类型检查与运行期行为跟 TS 有出入（对象展开、隐式返回类型、接口字段索引），靠读代码判断「应该能编过」在本项目失败过多次。

## 四、功能做完必须恢复到上游默认状态

**规则**：一处功能改完、验证完之后，把该功能的设置项恢复成上游默认值再交付，不要留在测试时用的取值上。

**为什么**：验证过程必然会改设置——改字号看排版、改主题看配色、开关一堆选项看差异。这些值留在设备上，下一个人接手时看到的不是「代码的默认行为」，而是「上一个人测试到一半的状态」。更麻烦的是它会被误读成缺陷：r299 取证时把 `readBarStyle` 改成 `2`、把 `readMenuBgColorNight` 改成 `#FF0000`，如果不清回，后续任何人打开阅读页都会看到红色顶栏，而默认值本来是跟随纸色。

**上游默认在哪里**：两份声明就是唯一事实来源，不要凭印象记：

- `domain/model/settings/ReadSettings.kt`（阅读设置，如 `:16` `textFullJustify: Boolean = true`、`:17` `textBottomJustify: Boolean = true`）
- `help/config/ReadBookConfig.kt`（书级配置，如 `:561` `private val pageAnim: Int = 0`）

本地对应 `entry/src/main/ets/data/ReaderSettingsRepository.ets` 的 `defaults` 对象（`:781` `textFullJustify: true`、`:782` `textBottomJustify: true`、`:810` `pageAnimation: 0`、`:811` `animationSpeed: 2`），三者必须逐项相同。**本地 defaults 与上游声明不一致时，以上游为准改本地，不是以本地为准改文档。**

**怎么恢复**：优先走应用内设置面板把值改回去；面板做不到的（如 `titleBarMode` 是字符串键、`readMenuLensRadius` 没有设置项）直接改设备上的偏好文件，再 `aa force-stop` + `aa start` 冷启复核。r299 记录的做法是 `sed` 就地改单个键后 `cp` 覆盖（`preferences/` 下新建文件会 `Permission denied`，覆盖已有文件可以；模拟器上没有 `run-as`）。

**交付前自查**：列出本轮改过的所有设置项，逐项对照上游默认值，确认已复原。这一条要写进验收说明——「已恢复到上游默认」是和「构建通过」「设备验收通过」并列的交付项。

## 五、ArkTS 类型约束易错点

- 不支持对象展开（`...obj`）用于类型化对象；需要复制时逐字段赋值或写显式拷贝方法。
- 变量名与字符串值不要指望一致：设置在存储里的键是**字面量**，不是变量标识符；改名时两者会脱钩。
- 索引访问接口字段时注意旧版本位移，解析器要同时兼容历史布局。

## 六、改文件的方式：脚本与编辑器不要混用

本节来自 2026-11-05 对全部会话日志的统计：**18 个会话共 138 次编辑失败**，其中 `file changed since it was read` 101 次、`old_string was not found` 32 次。逐条比对失败现场后确认，原因只有下面几条，与「文件里有不同的转义写法」无关。

### 1. 同一个文件不要「先脚本改、再编辑器改」

**规则**：一个文件在一轮工作里只选一种改写方式。要么全走脚本，要么全走编辑器；脚本写完若还要用编辑器改，先重新读一次文件。

**为什么**：编辑器读文件时记内容哈希，写之前再算一次；不一致就拒绝并报 `file changed since it was read`。python 脚本一落盘哈希就变了，紧随其后的编辑必然被拒。实测 101 次里按工具分：编辑器 68 次、整份写入 33 次、命令行 4 次——都是「刚用脚本动过」的位置。

**检查方法**：同一轮里改过某文件后，下一处改动要么继续用脚本，要么先重新读。

### 2. `old_string` 越短越稳，整段替换换工具

**规则**：定位用的片段只取能唯一定位的一到两行；需要大段替换时用整份写入或脚本，不要塞进 `old_string`。

**为什么**：32 次「找不到」里 23 条是多行片段，其中 4 条长 2386 / 2906 / 7685 / 8264 字符。逐条对齐后发现文件确实已经变了，不是转义对不上：

| 片段里写的 | 文件里实际的 |
| --- | --- |
| `preferences.getPreferences(context, ...)` | `RdbStore.getStore(context)`（r281–r284 迁到关系库） |
| 长按条目跳**转**正文并提示 | 长按条目跳**回**正文并提示 |
| 全表合计 **316** 条：已接 82 | 335 条：已接 87 |
| 含 `layoutDebugCount < 12` 的调试段 | 调试段已删 |

片段越长，命中历史任何一次改动的概率越高。长片段失配时先怀疑「文件变了」，不要怀疑工具。

### 3. 改之前重新读，不要凭记忆改

**规则**：要改的位置先读一次当前内容再写 `old_string`。

**为什么**：本项目常同时开多个会话，同一文件可能被另一会话改过；凭几轮之前的记忆写片段，必然失配。另外脚本或整份写入新建的文件**不算「已读」**，编辑器会报 `file has not been read`，先读一次即可。

### 4. 换行符：编辑器会归一，脚本必须自己保持

**规则**：用脚本整份重写文件时，`newline` 必须与原文件一致；改成别的换行符会让 git 把整份文件判成重写。

**为什么**：本仓库 `.ets` 实测 **71 个 CRLF / 137 个 LF** 混用（共 208 个文件），`core.autocrlf=true`，`README.md` 本身就是 CRLF。编辑器匹配时把 CRLF 与 LF 视为相同、写回时保留原样（已用 CRLF 探针文件验证）；脚本没有这层保护。

**检查方法**：脚本改写后看 `git diff --stat`，行数等于整份文件行数就是换行符被改了。

### 5. Markdown 表格单元格里的竖线要转义

**规则**：表格单元格内的 `|` 一律写成 `\|`；统计脚本一律逐字符扫描单元格，不用 `split('|')`。

**为什么**：本仓库曾有 6 个文件共 13 处漏写，后果不是渲染错位，而是**按列数解析的脚本整行丢弃**——`docs/parity/ZIP-COVER.md` 的 C5 行因两个未转义的 `||` 被切成 14 列，导致总账少算 1 行。转义竖线、正则里的 `\|` 都不影响编辑器匹配，只影响解析脚本。

### 6. 已排除的原因，不必再怀疑

以下都做过对照实验，**不是**编辑失败的原因：

- 三引号字符串 `'''` / `"""`：单引号三连、双引号三连、以及跨行内容，逐项匹配成功。
- 反斜杠转义：`\|`、`\u0000`、`\d+\(x)`、`"\\n"`、`"\n"` 五种形态全部匹配成功。
- 多会话并发写同一文件：138 次失败按小时聚合，同一时刻只有一个会话在活动，只有两小时出现过 2 次。

另外两个与本机环境有关的坑：python 里调 `subprocess` 会抛 `PermissionError: [WinError 5]`，需要外部命令时改由命令行执行；python 脚本里的 `\|` 在 heredoc 中会被 shell 吃掉，一律写成脚本文件并用 `chr(92)` 表示反斜杠。
## 七、功能做完的测试必须用真实数据

**规则**：一处功能做完后的验收，书和备份都优先用本机现成的真实材料，不要拿自己临时造的小样本走完就判「做完」。

- **真实书籍**：`N:\HarmonyProjects\测试\Book\`（仓库外，`txt/` 71 本 + `epub/` 75 本，编码覆盖 GB18030 / UTF-8 / UTF-8-BOM，体积 21 KB 到 102 MB，19 本带卷）。按测试目的挑，别一律拿最小的那本——该目录 `README.md` 有推荐档别名（TXT-超大章 8.5 MB / 1315 章是目录性能主测本、TXT-多卷 8.3 MB / 1088 章、EPUB-超大 102 MB）。
- **真实备份**：`N:\HarmonyProjects\测试\backup.zip`（2026-11-11，658 本书、344 条书签、904 个书源、41,629 条阅读会话、`config.xml` 372 个偏好项）与 `backup2026-10-22.zip`（同一批数据的上一个时间点，21 个条目集合完全相同）。新包数据量更大、`config.xml` 多 `read_aloud_capsule_offset_x` / `read_aloud_capsule_offset_y` 两键，优先用它。
- 两者都在仓库外，`.gitignore` 已含 `*.zip` / `*.epub`，不进 git；清单与逐条条数见 [备份与恢复](BACKUP-RESTORE.md) 的「测试样本」节。

**为什么**：两个理由，缺一不可。

1. **测负载**。真实数据量才暴露问题：2 章、200 字节的样本书跑得再顺，也测不出 1315 章目录的扫描耗时、658 本书的书架首帧、41,629 条阅读记录的聚合与热力图、904 个书源的整包导入。
2. **还原真实使用情形**。真实数据带着历史遗留：同一本书的重复条目、找不到对应书籍的孤儿阅读记录、跨午夜的读会话、GB18030 与 UTF-8-BOM 混编、上游写过而本地没写过的偏好键。合成样本天然干净，永远踩不到这些。

**何时才合成**：只有「必须精确构造一种畸形输入」时才造——缺正文的占位书、单条 `bookshelf.json` 的备份 ZIP、坏编码、超长单章、空数组与 `null` 边界。造出来的样本要在验收说明里写明它测的是哪个边界，不能用它替代真实数据的往返。

**交付时怎么交代**：验收记录里写清用了哪一份（文件名 + 本数/条数），真实材料没覆盖到的部分如实写「未验」，不要用合成样本的结果补齐。

## 八、跨页面共享的新状态进 @ObservedV2 Store，不再加 @Prop

**规则**：新写的跨页面共享状态，一律做成 `@ObservedV2` 单例 Store（类里字段用 `@Trace`），页面通过普通成员读取，**不再往 `pages/Index.ets` 加 `@State`、往页面加 `@Prop`**。存量不动。

**为什么**：现在是属性下钻——`@Prop` 全仓 783 个，`pages/Index.ets` 10,189 行、49 个页面组件被挂载（52 处调用）、传参键合计 1,729 个，其中 `ReaderSettingsPage` 一个页面被挂了四份（`:8351` / `:9140` / `:9519` / `:9816`，合计 1,200 行）。每加一个功能都要动同一个文件，边际成本落在它的行数上。结构的完整分析与改动量估算见[架构说明](ARCHITECTURE.md)第七节。

**怎么写（最简单的一条路）**：

```ets
// data/XxxStore.ets
import { AppStorageV2 } from '@kit.ArkUI';

@ObservedV2
export class XxxStore {
  private static instance: XxxStore | undefined = undefined;

  @Trace public playing: boolean = false;
  @Trace public position: number = 0;

  static get(): XxxStore {
    if (XxxStore.instance === undefined) {
      XxxStore.instance = AppStorageV2.connect(XxxStore, 'xxxStore', () => new XxxStore()) as XxxStore;
    }
    return XxxStore.instance;
  }
}
```

页面里当普通成员用，**不要**给它加状态装饰器：

```ets
@Component
export struct XxxPage {
  private store: XxxStore = XxxStore.get();  // 可以
  // @State store: XxxStore = new XxxStore();  // 编译报错
}
```

**三条会踩的坑**（依据官方《状态管理V1和V2混用指导》，页面更新于 2026-11-10）：

1. `@ObservedV2` 装饰的类**不能**塞进 `@State` / `@Prop` / `@Link` 等 V1 装饰器，编译报错。靠继承绕也不行——`class Sub extends ObservedV2Class` 再做 `@State` 是运行时报错。
2. `@ObservedV2` 只能装饰 class，不能装饰 struct；`@Trace` 只能装饰 `@ObservedV2` 类里的属性，不能用在 struct 里。
3. `@Trace` **不支持 Function 类型**——把回调存进 `@Trace` 字段，改它不会触发刷新。回调照旧用普通字段或参数传。

**第一个 Store 落地时先做五分钟验证**：写一个 `@ObservedV2` 计数器，在 `@Component` 里 `Text(String(this.store.count))` + 按钮 `this.store.count++`，确认数字会变。官方原文说会，本仓库也还没有先例（`@ObservedV2`/`@Trace` 全仓 0 处）；不变就说明这条路径在这台设备的运行时上不成立，停下来重新评估，不要硬推。（基线已由 `97c653b` 抬到 `6.0.0(20)`，`UIUtils.enableV2Compatibility` / `makeV1Observed` 因此可用；本节仍推荐普通成员写法，因为它不依赖任何兼容层。）

**存量怎么处理**：不主动改。只在新功能里用新写法；哪天要动某个存量页面，顺手把它那部分状态收进 store，不要为改而改。



## 九、用户感知范围内一律 1:1，多做少做都要举证

**规则**：**用户感知范围内一律 1:1**——界面、视觉、交互、功能、文案、动效、手感都在这个范围内，交付标准是「与上游一致」，不是「能用就行」。做不到 1:1 时，正确的动作不是换一种能跑的做法，而是先按本节三种证据之一证明**当前确实做不到**，把证据写进交付说明并标明用户感知到的差别，然后才降级。没有证据的近似值一律算缺陷，不算实现选择。

这条约束的起因很具体：让实现方做阅读域底栏时，上游 `labelSmall` 是 11sp，本地做成了 10 号，理由写的是「11 号时『自动翻页』四个字被裁」。真实原因是没有处理按钮宽度分配——降级把布局缺陷盖住了，而屏幕上少的那 1sp 用户看得出来。同类还有两处：探针失败后把面板高度写死成百分比、阴影在深色纸面上看不见就退成描边。三次都不是「做不到」，是「没想到」，但落到交付物上都是「与原版不一致」。

### 1. 三种可接受的证据

| 类型 | 证据形态 | 判定这句话成立的例子 |
| --- | --- | --- |
| 平台无此能力 | SDK 声明文件 + 行号 + 该能力在本平台缺失的原文 | `Scroll` 默认 `EdgeEffect.None`（`scroll.d.ts:1249`），平台没有「默认带弹性」这回事，回弹必须逐处显式声明 |
| 上游本来就不这么做 | 上游文件 + 行号 + 引用其代码或注释 | `readMenuColors` 只有 `2` 与 `else` 两档（`ReadBookMenuBar.kt:1033-1040`），不存在第三档配色 |
| 当前形态下不成立 | 可复跑的探测命令 + 原始输出 | 探针构建日志、`grep` 零命中输出、截图 + 复现步骤 |

三种都要落到**具体的文件:行号或可复跑命令**。写「SDK 不支持」「平台限制」而不给行号，等同于没有证据。

### 2. 不算证据的四句话

下面四种说法在本项目都出现过，一律退回：

1. **「这样更简单 / 实现起来麻烦」**——复杂不是理由，工作量不进入交付判定。
2. **「时间不够 / 额度不够」**——省时间省额度不是降级依据；做不完就停在那一条，写明未做，不要用一个近似成果顶上。
3. **「大概性能撑不住」**——没有 profile 数据或实测耗时的性能判断不成立；真怀疑性能就先把计时打点加上，用数据说话。
4. **「上游没写清楚」**——该去读上游源码，不是读上游的说明文档；上游文档与源码冲突时以源码为准（`PARITY-RULES.md` 第一节同理）。

### 3. 参数不取近似值

字号、行高、字重、间距、内边距、圆角、颜色（含透明度）、动画时长与缓动曲线、图标尺寸、触控热区、层叠顺序、文案措辞，全部照抄上游声明。差 1sp、差 1dp、差一个字数都算与原版不一致。

**开工时先把上游参数抄成一张卡**：还原某个控件之前，先把它的每个尺寸与颜色按「上游文件:行号 → 值」列出来，写在任务书或工作记录里；交付时拿这张卡逐项对本地实现。凭印象写「差不多 40」是本条最常见的失效方式，因为上游那个 40 往往带着 `glassEnabled ? 48 : 40` 这类条件分支。

### 4. 降级由判断段判定，实现段不得自决

遇到「做不到 1:1」时，实现段的动作是停下来交接，不是自己选方案。交接内容四项：上游要求什么（文件:行号）、卡在哪一步、试过什么、证据是什么。由判断段判成「真做不到」或「换个做法仍能 1:1」，判定成立才降级，并把结论写进对照表备注列。

理由见 [盘点规约](PARITY-RULES.md) 第五节：实现段的错误大部分有硬信号（构建失败、截图不对），但「屏幕上那个东西就是不对」这一类没有，而它恰好是降级最容易藏身的地方。

### 5. 留证格式

交付说明里按这张表写，一条降级一行。没有这张表就是没说清：

| 条目 | 上游值（文件:行） | 本地值（文件:行） | 用户看得见的差别 | 证据类型 | 证据 |
| --- | --- | --- | --- | --- | --- |
| 底栏动作文字字号 | `labelSmall` = 11sp（上游 `ReadBookMenuBarBottom.kt`） | 10 | 「自动翻页」四字不换行但比原版小一号 | 当前形态下不成立 | 探针截图 + 复跑命令 |

最后两列缺任何一个，这一行就不成立，条目按 `未接` 记。

### 6. 已经发生过的降级（当教训读，不要重复）

| 位置 | 当时的选择 | 正确做法 |
| --- | --- | --- |
| 阅读域底栏文字 | 11sp → 10 号，理由「被裁」 | 处理按钮宽度分配，字号保持 11sp |
| 阅读域设置面板高度 | 探针失败后写死百分比 | 继续查 Swiper 内的自适应约束，或把探针失败的原因写清后交回判断段 |
| 阅读域划词卡/搜索浮层阴影 | 深色纸面看不见 → 退成描边 | 阴影参数照抄上游，看不见是因为底色或层级不对，改那两处 |
| 动效任务书的页面转场 | 时长写 280 / 220 | 上游是 `NAV_SLIDE_DURATION_MILLIS = 480` / `NAV_FADE_DURATION_MILLIS = 360`，照抄 |
| 动效任务书的转场位移 | 用固定 vp 位移 | 上游按容器整宽位移（`initialOffset = { fullWidth }`），照抄 |

最后两行是任务书作者（也是本文件的维护者）写下的近似值，不是实现方擅自改的——**这条约束对写任务书的人同样成立**，任务书里写下的「简化版要求」会被实现方当规范执行。

### 7. 反方向同样成立：上游没有的不要自己加

本节前六小节治的都是「做得少」——上游有，本地没做，或者做成了近似值。**反方向更难发现**：降级会留下「这里少一块」的痕迹，自造不留痕迹。它能编译、能跑、点了有反馈，而且因为「符合逻辑」而让人相信它本来就该有；下一个会话读到这段代码，会把它当成上游行为，在上面继续垒。

**规则**：新增任何用户可见的东西之前，先给出上游对应物的 `文件:行号`；给不出就不许加。范围包括控件、设置项、页面、菜单项、图标、动画、文案。

**合法的「多」只有四种**，其余一律按缺陷处理：

| 类型 | 成立条件 | 必须写下的东西 |
| --- | --- | --- |
| 平台适配层 | 上游有，而平台没有该能力 | SDK 声明文件:行号 + 缺失原文 |
| 任务书批准的偏离 | 判断段明确批准 | 任务书条目 + 代码注释里的同一句话 |
| 架构差异导致的必要新增 | 本地数据模型与上游不同，导致上游不需要而本地需要 | 一句「上游为什么不需要」，写进代码注释 |
| 错误处理与空状态文案 | 上游没有对应分支 | 无，这类允许自行措辞 |

前三类都必须在代码注释里写明理由与上游对应物。**不写就等于把一个伪造的上游行为留给下一个人。**

**已核实的三处自造**（一处已删，两处待处理）：

| 位置 | 上游情况 | 状态 |
| --- | --- | --- |
| 阅读器顶栏下方五个圆钮（`struct ReaderControl`） | `ui/book/read/` 下没有「顶栏下方一排快捷图标」这个形态 | 已删（`13a3c1e`，3 文件 +6/−67） |
| `pages/AppDownloadCacheSettingsPage.ets:87` 的「整本正文内存缓存上限」滑块（字段 `bookContentCacheBytes` / `bookContentCacheMb`） | 上游 `domain/model/settings/DownloadCacheSettings.kt:3-12` 整个类只有 8 个字段，无此项；上游本地书正文用 8MB 定长字节缓冲逐段读（`model/localBook/TextFile.kt:30`），不整本进内存 | 已归类：架构差异导致的必要新增，保留。消费方 `data/BookRepository.ets:1784` |
| `data/CacheSettingsRepository.ets` 一带五个字段（`httpCacheSeconds` `preloadChapterCount` `coverCacheBytes` `imageCacheBytes` `clearCacheOnExit`） | 上游同名键零命中，本地 `pages/` 与 `data/` 下也无消费方 | 待处理：孤儿字段，删 |

第二条与第三条要分开看：第二条（`bookContentCacheBytes` / `bookContentCacheMb`）有真实消费方（`data/BookRepository.ets:1784` 用它决定整本正文要不要进内存缓存），属于「架构差异导致的必要新增」，正确处置是保留并补注释；第三条那五个字段才是纯孤儿，正确处置是删。**判据必须把 `data/` 层一起算进去**——`bookContentCacheBytes` 在 `pages/` 下确实零命中，只在 `data/` 里被读；只看 `pages/` 会把它误判成孤儿。**两者都不是「删掉就完了」，而是先归类，再按上表补注释或删掉。

**判别方法**：拿本地新增的字段名、设置项文案、控件形态去上游 `grep` 一遍。上游零命中不等于一定不能有（可能是架构差异），但**零命中就必须归类**，不能停在「反正能用」这一步。

**为什么归判断段管**：「上游有没有这个」本来就是判断段的准入条件（[盘点规约](PARITY-RULES.md) 第五节那张三行表），实现段没有这项裁量权。实现段觉得「这里应该有」就加一个，等于跳过判断段自行扩充范围。
